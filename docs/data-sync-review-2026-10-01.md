# 최신 데이터 동기화 검토 및 개선

## 운영 확인

2026-10-01 오전 운영 D1을 읽어 최근 8회 정기 동기화가 성공했음을 확인했다.
당일 실행은 09:10:50 KST에 시작해 09:11:26에 완료됐으며 원본 278건을 수집·반영했다.
공개 목록은 이전 스냅샷의 일시 누락 보존 항목을 포함해 284건이었다.
오늘 이전에 시작한 진행 중 행사도 최신 수집에 68건 포함됐다. 수집 날짜 조건은 유지한다.
운영 조회는 읽기만 실행했으며 데이터를 직접 변경하지 않았다.

## 확인한 문제와 수정

### 높음: 상세 재시도 시각 비교 오류

- 위치: `src/services/cultureSyncDetailRepository.ts`
- 기존: ISO 시각(`T`, `Z` 포함)을 SQLite `CURRENT_TIMESTAMP`와 문자열로 비교했다.
- 영향: 같은 날의 재시도 시각이 지나도 대상에서 제외됐다. 운영에서도 지연된 1건을 확인했다.
- 수정: 대상 조회, 사전 확인, 갱신 요청 모두 `datetime(detail_next_retry_at)`으로 비교한다.
- 호환성: 기존 ISO 값과 SQLite 시각을 모두 읽으며 요청 쿨다운과 백오프를 유지한다.
- 난이도: 낮음. DB 스키마 변경 없음.

### 높음: 외부 응답의 내용과 완전성 검증 부족

- 위치: `src/services/cultureSyncSource.ts`
- 기존: 총 개수가 맞으면 중복 ID가 포함된 페이지도 받아들였다. 필수 상세의 항목이 비어도 HTTP/API 성공 코드만으로 완전한 응답으로 처리했다.
- 영향: 페이지 경계에서 빠진 행사를 누락으로 판정하거나 기존 설명·요금을 빈 값으로 덮어쓸 수 있었다.
- 수정: 전체 수집에서 정규화된 content ID의 중복을 거부한다. 필수 기본·소개 상세가 없으면 저장을 중단하고 기존 상세를 보존한다.
- 호환성: 빈 이미지·부가정보 목록은 정상으로 유지한다. 일정, 분류, 목록 정렬, UI는 변경하지 않는다.
- 난이도: 낮음~중간. 불완전한 외부 응답에서 동기화를 거부하고 다음 복구 시 재시도한다.

### 높음: 캐시 기반 동기화 판단과 캐시 게시 실패의 복구 공백

- 위치: `src/server/cultureScheduledJobs.ts`, `src/services/cultureSyncRunRepository.ts`, `src/services/cultureSyncRecovery.ts`, `src/services/cultureSyncSchedule.ts`, `worker.js`
- 기존: 공개 health의 캐시 시각으로 재수집을 생략했다. DB 반영이 성공하고 KV 게시만 실패해도 최근 성공으로 처리해 오래된 공개 캐시를 유지할 수 있었다. 오전 복구도 실패하면 다음 날까지 원본 복구 기회가 없었다.
- 수정: D1 실행 이력을 기준으로 판단하고, 필요한 작업은 락 획득 후 다시 확인한다. DB 원본이 최신이면 실제 목록 내용·revision·게시 시각을 비교해 캐시만 복구한다. 시간당 기존 크론에서 실패한 원본 또는 26시간 초과 원본을 재시도한다.
- 호환성: 정상 원본 수집은 매일 09:10 KST, 오전 복구 확인은 10:10이다. 매시 17분에는 복구 점검 후 상세를 점진적으로 갱신한다. 정상 복구 점검은 DB/KV 조회만 수행하며 락·KV 쓰기나 외부 원본 재수집을 하지 않는다.
- 난이도: 중간. 운영 캐시 게시 흐름에 영향이 있어 D1·KV 통합 테스트와 브라우저 회귀 검증이 필요하다.
- 비용: 정상 시간당 복구 점검에 D1 실행 이력 1건과 현재 목록 비교 조회가 추가된다. 점검에 따른 추가 외부 수집·캐시 게시는 복구가 필요한 경우에만 발생한다. 기존 정기 수집과 상세 갱신 비용은 유지된다.

## 검증

각 수정은 lint → typecheck → 관련 테스트 → 전체 테스트 → Next.js build → Cloudflare build와 모바일·데스크톱 E2E 순서로 검증한다.
SQLite를 실제 실행하는 통합 테스트는 CI와 동일한 Node.js 22에서 수행한다.
Node.js 20에서 실행하면 SQLite 통합 테스트는 명시적으로 skip되고 나머지 테스트는 계속 실행된다.

주요 회귀 사례:

- 과거 ISO 재시도 시각을 선택하고 미래 재시도와 요청 쿨다운은 유지한다.
- 빈 필수 상세를 받으면 저장된 설명·요금을 유지하고 백오프를 기록한다.
- 중복 페이지, 잘린 목록, 수집 중 전체 건수 변경을 반영하지 않는다.
- 공개 캐시가 최근이어도 D1 원본이 오래됐거나 실패한 경우 복구한다.
- KV 누락과 내용 불일치를 원본 재수집 없이 복구하며 누락 횟수를 보존한다.
- KV 게시 실패를 숨기지 않고 DB·이력·기존 데이터를 유지하며 락을 해제한다.
- 다른 실행의 락을 존중하고 정상 시간당 점검에서는 쓰기와 외부 요청을 하지 않는다.

외부 API 장애와 캐시 쓰기 실패는 격리된 테스트에서 재현한다. 실제 운영에서 장애를 주입하지 않는다.
배포·CI/CD·운영 smoke 결과 및 배포 이후의 실제 크론 실행 결과는 작업 완료 보고에 별도로 기록한다.

로컬 결과: lint/typecheck 통과, 전체 테스트 319개 통과, Next.js/OpenNext 빌드 통과,
최종 모바일·데스크톱 E2E 60개 통과. 첫 두 수정도 각각 전체 테스트·빌드·E2E를 통과한 뒤 다음 수정으로 진행했다.

### 검증 중 관찰 항목

마지막 전체 E2E의 첫 실행에서 모바일 404 화면 테스트가 한 번 일시 오류 화면으로 전환되어 실패했다.
같은 테스트를 모바일·데스크톱에서 10회 반복했을 때 모두 통과했고, trace를 수집한 전체 60개 재검증도 통과했다.
원인은 미확정이다. 관련 페이지와 UI를 임의로 수정하지 않았으며 재발 시 trace와 운영 로그로 별도 진단한다.

## 유지하는 설계

스테이징 격리, 단일 batch 반영, 70% 급감 방지, 2회 연속 누락 후 비활성화,
소유권 락과 하트비트, 상세 실패 시 기존 데이터 보존, KV 우선 공개 조회와 D1 read-through를 유지한다.
현재 규모에서 새 큐·Durable Object·실시간 원본 수집으로 교체할 실익은 확인되지 않았다.
원본 API의 등록 지연과 외부 서비스 장애는 애플리케이션에서 직접 제거할 수 없다.
